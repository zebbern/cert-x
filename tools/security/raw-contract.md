# Raw transport contract

The native action prefix is `transport.`. A raw operation uses one service concurrency slot for its full lifetime. Every TCP/TLS connection invokes admission with `request.kind: "raw_connect"`; every write attempt invokes `request.kind: "raw_send"`. Both carry `request.targets: [{url, method, ...}]` for all decoded logical routes. The admission bridge receives `{...context, request}` and rechecks current scope and revocation. Control-only evidence reads invoke `request.kind: "control", request.backend: "transport"`.

## Actions

| Action | Inputs | Behavior |
| --- | --- | --- |
| `transport.http1` | `url`, canonical `requestBase64` | Sends the exact decoded bytes over TCP or TLS. Complete, routable HTTP/1 request lines, authorities, and paths must be in scope. Pipelined and request-looking nested interpretations are checked. |
| `transport.http2` | `url`, `requests` or `frames`/`bytesBase64`; optional `preface` | `requests` uses pinned `hpack.js` 2.1.6 and emits SETTINGS, HEADERS, and DATA frames. Structured DATA is split into frames of at most 16,384 bytes. Frame mode preserves exact `rawBase64` or serializes `{type,flags,streamId,payloadBase64}`. Raw HEADERS/CONTINUATION blocks are HPACK decoded; decoded routes and request-looking HTTP/1 content inside DATA are checked before connection. HTTP/2 over TLS requires ALPN `h2`; cleartext h2c uses the client preface. |
| `transport.websocket` | `url`, optional `handshakeBase64`, `frames` | Sends a complete HTTP/1.1 upgrade request. It waits for a complete 101 response with matching `Sec-WebSocket-Accept`, `Upgrade`, and `Connection` before sending any supplied frame bytes. The exact handshake and frame bytes are retained. |
| `transport.desync` | `optIn:true`, `protocol`, paired probe/control and either observation or `responseQueue` configuration | Backend observation mode runs reset, negative control, probe, and observation on fresh admitted connections for each repetition. HTTP/1 response queue mode uses only the front connection and requires explicit front framing, complete request boundaries under both framing policies, and fully parsed response sequences with controlled route and marker pairs. Both modes require at least two paired repetitions. Timeouts alone never confirm. |
| `transport.evidence` | `evidenceId`, optional byte `offset` and `limit` | Returns an owner, run, and workspace bound page of the persisted JSON record as canonical base64, with `total` and `nextOffset`. Default page is 65,536 bytes; maximum is 131,072 bytes to fit native messaging. |

`transport.http2` supports `requests:[{method,path,headers,bodyBase64,streamId}]`; `headers` can be a map or ordered `{name,value}` list. Structured request bodies are bounded to 65,535 bytes per stream and in aggregate per connection, matching the initial HTTP/2 flow-control windows; window-update negotiation is not implemented. Use explicit raw frames for larger sequences with caller-managed flow control. A structured request raises an error with persisted evidence on RST_STREAM, error GOAWAY, or missing complete response. SETTINGS-only and other routing-free frame tests require `allowControlFrames:true`. Existing `frames`, `bytesBase64`, `preface`, `requestBase64`, `handshakeBase64`, `timeoutMs`, `maxResponseBytes`, `delayMs`, `endAfterWrite`, and `ignoreTlsErrors` remain accepted where relevant. `maxResponseBytes` is a capture limit, not a request budget. Captured truncation is explicit. The transport returns `evidence.evidenceId`, a SHA-256 digest and byte count for the private persisted record. Results that fit the native frame include sent and returned base64; larger results provide a summary and are read through `transport.evidence`.

Desynchronization HTTP/1 uses `requestBase64` and `controlBase64`. HTTP/2 uses `requests` or `frames` for the probe and `controlRequests` or `controlFrames` for the control. `repeats` defaults to 2. `reset` is `{url,requestBase64}` and must return one complete HTTP 200 response with valid framing. `observation` is `{url,requestBase64,expectedPath}`; the endpoint must return one complete HTTP 200 response with JSON body `{"requests":[{"path":"/observed"}]}`. The reset and observation URLs, their wire request routes, and `expectedPath` must be in scope. Without reset or with missing, malformed, truncated, or contradictory observations, classification is `inconclusive`. All attempts and partial errors retain private evidence IDs.

Response queue mode is HTTP/1 only. Set `responseQueue:{frontFraming:"cl",outer:{route,marker},followup:{route,marker},injected:{route,marker}}` for a Content-Length front, or use `frontFraming:"te"` for a Transfer-Encoding front. The alternate policy is treated as the backend. Routes must be distinct origin-form paths; markers must be distinct controlled strings and absent as UTF-8 byte sequences from both raw wire requests. `requestBase64` and `controlBase64` must be canonical base64. The separate scope validator checks every request-looking route. A complete-boundary parser then requires the control to parse as `[outer,followup]` under both policies, and the probe as `[outer,followup]` under the declared front and `[outer,injected,followup]` under the alternate. An ordinary three-request pipeline, incomplete framing, a wrong route sequence, or a marker present in request bytes fails preflight before network traffic. The strict boundary parser supports complete CL and chunked TE messages with CRLF framing and a zero chunk without trailers.

Each response body must be JSON with `route` and `marker` matching the controlled values. Each fresh connection must yield complete HTTP 200 responses in the control `[outer,followup]` or probe `[outer,injected,followup]` order. This sequence and at least two paired repetitions classify as `confirmed_with_response_queue`; any timeout, truncation, incomplete response, different status, marker mismatch, or inconsistent sequence is `inconclusive` with evidence. The result includes `framing:{front,alternate}` and `boundaries:{controlBase64:{cl,te},requestBase64:{cl,te}}` route arrays. No backend telemetry is used. The marker source must be a controlled backend route; absence from request bytes prevents literal reflection from establishing attribution. Proxies that suppress or rewrite surplus responses will not support this confirmation mode.

## Interpretation limits

The validator rejects unknown or incomplete routing rather than relying on the declared connection URL. HTTP/1 requires CRLF request framing; bare-LF request boundaries and opaque leading bytes are unsupported. HTTP/2 requires complete frames and decoded HPACK request headers. PUSH_PROMISE and unknown extension frame types are unsupported. HTTP/2 CONNECT without ordinary method/scheme/authority/path is unsupported. The validator inspects request-looking HTTP/1 bytes in HTTP/2 DATA, but cannot prove how every nonconforming proxy will reinterpret arbitrary binary data. A successful send is transport evidence; a desync confirmation describes only its controlled fixture and paired controls, not general behavior of other deployments. The WebSocket, HPACK smoke, evidence paging, and cancellation tests are plumbing evidence. The CL/TE fixture tests use independent message parsers and rejecting/normalized negative configurations.

Native errors after admission include the persisted raw evidence ID in their message. Each record contains the exact captured response bytes, attempted and completed writes, connection timing/TLS metadata, timeout/truncation flags, and error text. Cancellation destroys the owned socket and settles the operation. Evidence is stored under the configured managed runtime root in `raw-evidence`, with 0700/0600 modes where supported; no list action is exposed.
