# Stored XSS positive browser verification

Run `node tools/security/tests/stored-positive.browser.cjs` from the repository root. The script hash-verifies the supplied unmodified PTK 10.0.0 source through `prepare-reference.cjs`, copies it to a disposable extension directory, and runs the original and integrated runtimes sequentially in separate isolated Chromium profiles. It writes raw planner, request, response, mutation, confirmation, event, and fixture-wire records to `tools/security/evidence/stored-positive.json`. The existing `stored-marker-collection.browser.cjs` remains a separate negative regression.

The supplied `stored_xss_blind` pro entry is metadata only in both runtimes. There is no executable imported stored-XSS rule to run. This fixture derives one valid active module from each runtime's imported canonical XSS rule, changes its ID to `stored_xss_blind`, and uses the same fixture payload, marker, and tracking configuration in both. It calls the actual rulepack validator, task planner, task runner, request replay, stored tracker, privileged browser adapter, and browser-nav confirmation harness. The baseline POST is supplied as a captured request to the planner so the test sends only one state-changing submission. The synthetic payload changes only `data-ptk-xss` on the local page's document element when its event handler runs; the test makes no external callback.

The resettable localhost fixture has five matched cases. `executing` stores an HTML event handler and confirms execution after a GET retrieval. `escaped` stores the same bytes but renders them as escaped text. `retrieved_only` returns the marker inside an inert `template`. `no_retrieval` withholds the marker. `authenticated` logs in as synthetic account `fixture-alice` using the local fixture password, then requires that session for the POST and view. The captured session cookie is placed in PTK's replayed request; the isolated browser already holds it for confirmation. This exercises a multistep authenticated stored surface with matched accounts and route conditions. It does not claim to exercise PTK's separate `browser_workflow` runtime mode, whose implemented flow is `auth_2fa_bypass` and whose task branch does not call stored tracking.

Every case compares the original and integrated request sequence and body after projecting only PTK's per-run `ptk_rnd` nonce and incidental favicon requests. It also compares planner target, mutation, confirmation proof, and runtime event type/reason/error. Assertions require exactly one POST mutation per side, one planned `comment` target, no browser or engine error, an executed browser confirmation with an attribute event-handler context for positive cases, and no finding for the three controls. The escaped and inert-template controls must reach `dast_stored_xss_retrieved_unconfirmed`. The authenticated planner's hard-deny skip of the `sid` cookie as an attack target is expected and checked on both sides; it does not block the `comment` mutation.

The fixture establishes parity for this bounded browser-confirmed stored execution path. It does not establish parity for a real pro stored-XSS attack catalog, additional payload contexts, other application authentication patterns, or the unrelated 2FA browser-workflow engine. Integrating an actual stored module requires an executable canonical rule, not a metadata entry; that module should then be added to this matched browser matrix without replacing the execution and negative-control assertions.
