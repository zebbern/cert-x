# PTK v10 companion

From the cert-x repository, run:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\ptk\build.ps1 -ExtensionId YOUR_32_CHARACTER_EXTENSION_ID
```

The default source is `..\insp\pentestkit-10.0.0-release`. Use `-Source` for another copy of the same release. The original source is hashed and copied to `%LOCALAPPDATA%\cert-x\ptk\v10`; dependencies use its unchanged lockfile. The compatibility patch described below applies only to this prepared copy. Existing unrecognized or differently sourced output directories are refused. No browser is modified automatically.

In `chrome://extensions`, enable Developer mode and **Load unpacked** the printed `src` folder. Keep PTK enabled alongside cert-x in the same browser profile. The copied development configuration permits PTK's explicit per-tab activation handshake; merely loading it does not start a scan.

The preparation uses upstream `build_src` stages and the supplied detection databases. It deliberately skips `build_waf`, which downloads data from moving upstream branches. `cert-x-build.json` records the source hashes and build commands. The PTK license and upstream notices remain with the companion copy.

Compatibility revision 1 (`compat.cjs`) adds a capability marker, reserves IAST startup/stopping, refuses cert-x enrollment into an existing IAST engine, limits cert-x instrumentation to its selected tab instead of registering origin-wide startup scripts, and exposes ownership/drain diagnostics. Its navigation fallback uses the selected tab's exact origin, and findings stay bound to the session's native scan ID instead of substituting the current engine's results. Other upstream features remain in the prepared extension. Each changed file's original and patched hashes is recorded in `cert-x-build.json`; unknown output edits are never overwritten. Rerun `build.ps1` to apply the patch to a recognized earlier preparation without another dependency install, then reload PTK, cert-x and the target page. Current-document injection and reinjection can happen after page load; cert-x reports that coverage gap.

Targeted DAST revision 5 (`dast-patch.cjs`) installs a separate bounded coordinator around PTK's existing request builder, mutation and validation APIs. It uses the bundled `xss_1`–`xss_3`, four `sqlinjection_*` definitions and the `redir_1` replacement action. Each family has its own evidence rules. SQL error checks compare two baselines plus a benign control and require repeat confirmation. Redirect checks compare the complete parsed Location against a unique reserved marker; body reflection is insufficient.

Only selected query/form fields and JSON string tokens are mutated. `dast-inputs.js` is shared with cert-x's capture adapter and identifies JSON leaves by pointer and ordinal without rounding numbers or rewriting unrelated bytes. Duplicate keys and non-string selections fail explicitly. Request IDs, exact URL/method and companion initiator correlate temporary nonblocking header observers to the single dispatched request. They recover manual-redirect status/Location without enabling PTK's global tracking listeners or following a redirect.

Baselines, benign controls, mutations and confirmation requests share a one-request/second, concurrency-one budget, capped at 100 requests and 300 seconds. Redirect following and transport retries remain disabled. Evidence labels distinguish reproduced reflection, SQL errors and HTTP redirects; they do not claim browser execution, query control or downstream impact. Boolean/time-based SQL checks remain follow-up work.

`pairing.cjs` writes `providers/ptk-connection.json` in cert-x (Git-ignored) and `src/cert-x-connection.json` in the companion. They contain a local shared key and cert-x's extension ID; neither is web-accessible. The companion's external-message allowlist restricts the caller to that ID. cert-x authenticates a page-suggested companion address with a fresh HMAC challenge before sending private captured requests. Existing keys are preserved, mismatched keys fail explicitly, and provenance metadata never includes the key. Keep these local configuration files out of shared bundles. Copy the setup command from PTK settings rather than guessing the extension ID. Later runs can omit `-ExtensionId` when pairing already exists.

DAST results remain in companion memory; only lifecycle tombstones persist in session storage to prevent replay after worker restart. Save JSON reports before reloading the companion. Up to 32 batch identities are retained per browser session; restart the browser after exporting if that limit is reached. DAST and cert-x analysis/observation are admitted separately. Do not start a separate manual PTK scan during a cert-x batch.

Revision 4 adds a separate account-comparison coordinator and isolated transport. Explicit credential snapshots are applied with fetch credentials omitted, exact-origin/URL/method/no-tab DNR session rules, and response cookie removal. The worker serializes comparison/verification with injection batches, blocks overlapping PTK request-builder, scan and HTTP fetch work, and rejects admission while earlier work is pending. Independent extension tabs are excluded from credential rules. Original browser cookies are never replaced. Interrupted owned rules are removed at startup; failed cleanup blocks further requests. Identity probes and known-object evidence are checked around comparisons; only repeated unexpected protected access becomes a finding. Full response bodies, credentials and configured expected values are not exported.

Revision 5 adds exact query/form occurrence mutation, cert-x bounded Boolean SQLi and template-evaluation strategies, and PTK JSONP plus passive response modules. Boolean/template strategies are identified separately from upstream rulepack definitions. JSONP and passive matches are observations; every selected check has explicit tested/skipped/unsupported/inconclusive coverage, preserved across partial budgets and exports. Passive modules inspect the baseline only, including suitable error responses, and never follow discovered URLs. Mutation bodies are constructed lazily and retain untouched bytes. Expanded checks/repeated inputs require revision 5 and ordinalInputs capability before approval.

The expanded real fixture suite uses Node with node:sqlite and Python with Jinja2 (tested with Node 24 and Jinja2 3.1.6); set PYTHON_PATH if needed. It exercises real SQLite query behavior and sandboxed Jinja expression rendering in an isolated local application, alongside reflection, unstable-response and parameterized controls. No packages are installed by that test.
