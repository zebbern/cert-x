# Agent security investigation evaluation

The product target is a better investigator than the same model with browser tools alone: more independently supported vulnerability classes, less time to useful evidence, and a complete, accurate report. Raw scanner alert counts and route visits are supporting diagnostics, not the score.

## Controlled comparison

`tools/security/tests/dvwa-live.browser.cjs` runs actual, paid `xiaomi/mimo-v2.6-pro` inference through OpenRouter (key read from `.env.local`) in an isolated Chromium profile with cert-x installed. The harness initializes the provider, target session, and optional login; it does not script scan starts, browser actions, findings reads, or report text. `CERT_X_LIVE_SCENARIO=natural` sends the same ordinary task to two arms. `CERT_X_LIVE_ARM=certx` selects Bug bounty; `browser-only` inherits Default, which has no security tools. The baseline still runs inside cert-x's browser shell and can see its global security-testing skill, so it is a conservative browser-only proxy, not an exact ChatGPT/Codex tool environment.

Use separate, disposable DVWA databases so an account change or stored payload in one arm cannot alter the other. `tools/security/tests/fixtures/dvwa-compose.yml` pins the official [DVWA Docker image](https://github.com/digininja/DVWA/blob/master/README.md?plain=1) and MariaDB by digest; it binds only to loopback. `prepare-dvwa.cjs` initializes the database and verifies the default training login. The harness pre-authenticates both arms and selects DVWA's low security level, recording that setup separately from model actions. It does not ask the model to reset the database during a run.

Example setup, using two distinct project names and ports:

```powershell
$env:CERTX_DVWA_PROJECT='certx-dvwa-eval-a'; $env:CERTX_DVWA_PORT='4281'
docker compose -f tools/security/tests/fixtures/dvwa-compose.yml up -d
$env:CERTX_DVWA_PROJECT='certx-dvwa-eval-b'; $env:CERTX_DVWA_PORT='4282'
docker compose -f tools/security/tests/fixtures/dvwa-compose.yml up -d
node tools/security/tests/fixtures/prepare-dvwa.cjs http://127.0.0.1:4281 http://127.0.0.1:4282
```

Run the two arms sequentially with `CERT_X_LIVE_TARGET` set to their own origin, `CERT_X_LIVE_PREAUTH=1`, `CERT_X_LIVE_SCENARIO=natural`, the appropriate `CERT_X_LIVE_ARM`, and a recorded `CERT_X_LIVE_PRIOR_COST_USD`/`CERT_X_LIVE_TOTAL_COST_USD` accounting ceiling. The harness supports explicit model-turn, time, tool-idle, scanner-request, rate, and concurrency bounds through `CERT_X_LIVE_MODEL_REQUESTS`, `CERT_X_LIVE_DURATION_MS`, `CERT_X_LIVE_TOOL_IDLE_MS`, `CERT_X_LIVE_SCAN_REQUESTS`, `CERT_X_LIVE_SCAN_RATE`, `CERT_X_LIVE_SCAN_CONCURRENCY`, and `CERT_X_LIVE_PLANNING_CONCURRENCY`. Local fixture defaults match Thorough's concurrency 3/planning 2; the public shared-lab mode retains 1/1. Bounds belong to the evaluation, not the user's normal Thorough preset. The retained JSON records the exact bounds, model calls, tools, traffic, run state, and report path. Run `node tools/security/tests/compare-agent-runs.cjs <certx.json> <browser-only.json>` for a numeric comparison; adjudicate each claimed vulnerability against its retained request/response or browser-execution evidence separately.

## First completed local pair, 2026-10-23

Both arms used the same model and task on separately initialized copies of the pinned DVWA image. The cert-x arm finished in 434 seconds with 26 model requests, 18 module paths, 356 scanner requests, 15 raw alerts, and a final report. Browser-only finished in 310 seconds with 55 model requests, 18 module paths, 102 browser requests, and a final report. **This earlier harness fixed scanner concurrency at 1**, below Thorough's normal 3, while the browser-only model could issue parallel CDP calls; its elapsed-time gap cannot be presented as a normal-default speed comparison. The cert-x report described seven application classes with concrete probes; the browser-only report described more classes. Neither report's labels are accepted as independent confirmation without checking the tool evidence. In particular, cert-x incorrectly said its 1,200-request evaluation cap was reached when the run used 356 requests; the agent had stopped the scan early. The browser-only report made broad claims about brute-force resistance and configuration disclosure from narrower observations. These runs do **not** establish that cert-x is faster or finds more verified bugs.

Private raw records, including the reports, are retained under `%LOCALAPPDATA%/cert-x/verification` as `dvwa-natural-certx-2026-10-23T00-03-16-898Z.*` and `dvwa-natural-browser-only-2026-10-23T00-11-01-732Z.*`. The comparator refuses different models, task prompts or evaluation bounds. Its totals are execution measurements; scanner alerts and model prose remain unadjudicated.

A subsequent cert-x-only local run with breadth-first scheduling and scoped HTML-link discovery finished its original chat in 667 seconds and 81 model requests (`dvwa-natural-certx-2026-10-23T01-13-21-203Z.*`). The scanner reached 18 module paths, dispatched 2,006 of a permitted 5,000 requests, and retained 56 raw alerts. The model reported eight vulnerability classes with varying proof strength. It was still slower than the 310-second browser-only arm, so neither the scheduler nor link discovery establishes the product target yet. Its final prose called the remaining DAST work a small 13-task gap, while the retained counters show 6,707 planned and 4,167 entered; that mismatch prompted explicit terminal accounting-gap reporting. A later extended trial reached a file-upload tool stall after `save_file`; the retained record `dvwa-natural-certx-2026-10-23T00-32-52-005Z.json` has no terminal model report and must not be counted as success.

After correcting the local scanner concurrency to Thorough's 3 workers and 2 planners, a fresh completed pair used the same pinned image, model, prompt, and pre-authenticated low-security setup. Cert-x (`dvwa-natural-certx-2026-10-23T02-17-03-269Z.*`) finished in **430 seconds**, 53 provider requests, 18 module paths, 1,463 scanner requests, and 56 raw alerts. Browser-only (`dvwa-natural-browser-only-2026-10-23T02-27-50-404Z.*`) finished in **404 seconds**, 108 provider requests including its route-mapping subagent, 18 module paths, and 399 browser requests. One earlier browser-only attempt ended prematurely because the harness mistook a child `finish_reason:stop` for parent completion; that attempt is retained but excluded. The browser-only final report claimed more classes, while cert-x provided scanner corroboration and a stronger direct DOM-XSS reproduction. Neither report's claims have been fully independently adjudicated. This corrected pair still does **not** establish that cert-x is faster or finds more verified bugs; the 26-second difference is one stochastic trial, not a population estimate.

Focused browser tests verify an in-memory `upload` of exact agent-created bytes, including while DAST is active. Local-path uploads are bounded to return an actionable timeout if Chrome's debugger command stalls after a download; an in-memory generated upload avoids that path. The start tool also returns a scoped, value-free route/form inventory so the agent can plan broad coverage without rereading entire pages. A cert-x-only run with both features (`dvwa-natural-certx-2026-10-23T01-42-16-247Z.*`) finished autonomously in 525 seconds: the model received 25 scoped links at start, visited or scanned 18 module paths, used `upload.generated` and verified PHP execution, and retained 37 raw alerts. Its terminal accounting correctly said 1,507/5,000 requests and a 2,339 planned-versus-entered task difference. Its narrative still incorrectly called the upload unauthenticated despite the pre-authenticated fixture and claimed a password restoration that did not restore the original training password. A fresh *paired* live-model superiority result with the final bundle remains to be measured; the completed browser-only arm took 310 seconds on the same pinned fixture family.

## Acceptance for future changes

Compare at least three paired runs on reset fixtures with the same model, task, login state, available time, and application version. Record time to first reproduced class, distinct reproduced classes by a fixed checkpoint and at terminal response, false or unsupported impact claims, untested routes, scanner probe distribution, and whether the agent completes its report without a follow-up. Separate provider latency from scanner and browser wait time. Treat an exhausted evaluation bound, a user-stopped scan, and a completed finite scan as different outcomes. A scanner finding counts only when its retained evidence supports the claim; a model's plausible description of a vulnerable module is not proof it exercised that module.
